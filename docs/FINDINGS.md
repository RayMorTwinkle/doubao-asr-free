# 豆包输入法 ASR 协议观察与恢复陷阱

实测日期：2026-10-26、2026-10-27。以下是有限样本与特定环境下的观察，逆向接口可能变化。
本次补充包含独立可运行的合并/故障回归测试及采集脚本，不需要访问作者的私有音频目录。

## 先记住三件事

1. **服务器已消费音频不代表文字已落盘。** `audio_duration_ms` 是进度，不能直接当崩溃恢复断点。
2. **空 FINAL 不代表丢弃当前挂起句。** 原始响应里，空 FINAL 之后其他句子的中间结果仍在继续。
3. **参考转写也会截断。** 如果没有确认输入发完并收到 `SessionFinished`，不得把产物当作完整参考。

## 响应结构

| 观察 | 对使用者的影响 |
|---|---|
| `is_interim=false` 且无 VAD finished 的结果后，还会继续更新同一句 | 单独暴露 `TWO_PASS_RESULT`，不要提前认定结束 |
| `results[].index` 在样本中一直为 0 | 不能用作唯一 utterance ID |
| 结果级或词级时间戳曾出现两倍偏差、漂移或超出总时长 | 不能用于恢复断点、精确定位或“无漏转”证明 |
| `extra.audio_duration` 以毫秒报告消费进度 | 已映射为 `ASRResponse.audio_duration_ms`；仅用于进度观察 |
| 句子结果可交错，最终稿可晚到、加长或缩短 | 需要修订已有记录，不能仅追加或按前 15 字丢弃新稿 |
| 部分 FINAL 包含上一段中间结果的较长尾部 | 同时检查源范围重叠提示和长尾首匹配，保留原文以便检查 |

`StreamingMerger` 由 `transcribe()` 与实时应用共用：处理空 FINAL、迟到修订、最终稿更正，保留位于稍后音频位置的真实重复。
其 start_time 和文本匹配仍属启发式，不能消除所有误分句。行上 `raw_text` 保留去重前文字。

## 崩溃恢复应使用持久化安全点

反例：服务器消费约 12 秒时，没有一句定稿落盘，只有 54 字挂起结果在内存。
如果把消费位置存成断点，闪退后仅回退 2 秒，前约 10 秒既没有文字也不会重发。
某次实验回退 2 秒接力成功，不构成通用保证。

一种容易审计的策略是将输入组成有界会话事务，例如每 120 秒正常 FinishSession：

- 只有客户端完成输入、服务端确认 SessionFinished 后，才将结果与安全点一起原子写入。
- 未完成会话的音频在重连时整段重放，并替换当前尝试的临时文字。
- 录音先独立落盘，转写升级或失败不停止录音。
- 发送、消费、已归档是三个不同的进度量。

正常协议收尾代表服务完成处理，不等于识别逐字正确。长音频切分也会改变上下文与识别措辞。

## 速率、空闲与静音

在旧样本中，不限速发送 600 秒音频后出现 RST_STREAM，服务器最后报告消费约 436 秒；
6x 匀速实验则有连续约 10 分钟存活的记录。这支持速率或缓冲相关假设，**并未证明网关内部缓冲溢出就是唯一原因**。
约 6.4x 是当时观察到的消费速度，不是吞吐 SLA。不要向服务器瞬间倾倒整段长音频。

旧实验还观察到 150 秒零输入和 480 秒静音期间会话存活，但暂停后恢复时也出现过主动结束会话。
因此可以避免为了“保活”不断发送静音，同时仍需处理任意时刻的断连、重连与重放。

## 会话字段的实际生效情况（2026-10-27 补充）

同一段 90 秒音频做单变量六臂实验（内容级对比，剥离遥测字段）：

- 服务端**只读 `enable_speech_rejection`**：开启后在窗口收口响应上多出 `extra.speech_rejection_result`（reject/confidence/lmscore/snr_class/text_token_num），处理明显变慢（首响应 712ms→2042ms），文本输出不变。
- rejection 判定近似窗口长度换算（每字 lmscore 恒定，总分 ≤-100 判拒），confidence 是该窗口 ASR 置信度的回显；无实用过滤价值，保持默认关闭。
- `enable_punctuation`、`enable_asr_twopass`、`enable_asr_threepass`、`app_name`、`input_mode`、`strong_ddc`、`use_twopass_retry` 均被无视：输出与基线逐一致（关闭标点后标点照发）。
- 未发现多结果帧、句子级历史或隐藏修订通道；`semantic_related_to_prev`、`oi_words` 恒为 null。合并器不能指望服务端下发历史，只能在客户端维护；无标点输出需客户端后处理。
- `model_avg_rtf`、`model_send_first_response`、`model_total_process_time` 每次运行都会变化，做内容对比时必须剥离。

随实验对库的改动：`ASRConfig` 与会话 extra 增加可选字段 `input_mode`、`strong_ddc`、`use_twopass_retry`（不设置则不写入 payload，`exclude_none` 序列化，默认 payload 与旧版逐字节一致）。

## 本次代码改进

- 全文转写不再只返回最后一句 FINAL；使用共享修订合并器。
- 编码器、音频源或发送任务失败时立即传播，不再永远等待接收队列。
- 接收端结束时取消仍在等待新音频的发送器，避免暂停时断连后挂住。
- 输入完成后等待最终结果有超时；初始化响应也有超时。
- 缺少 SessionFinished 的连接结束明确返回错误，不能静默提供“看似完整”的部分结果。

新响应类型可能影响只处理 INTERIM_RESULT/FINAL_RESULT 的调用者：需要同时处理 TWO_PASS_RESULT。
这组本地修复尚未作为新的公开版本发布，不应假设 GitHub 默认分支已包含它们。

## 验收不能混为一谈

- 音频哈希或字节比较：证明录音保存了什么。
- 完整供给、正常结束、原子归档：证明客户端处理了哪些音频块。
- 全文字符对齐或人工抽查：评估识别内容，不能拿首尾锚句存在来推断中间完整。
- “字数差不多”以及人为补成连续的时间区间，都不能证明没有漏转。

一次 600 秒旧参考实际只到约 436 秒；先前将新输出比它多约 45% 主要解释为重复，是错误归因。
重建完整参考后，两种会话切分的字符对齐约 93%，仍有服务识别差异和局部低一致度，必须如实报告。
